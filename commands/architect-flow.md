## Step 4 — evaluate gate.flow yourself

Read both files and check:

- every flow names an actor and a trigger
- every flow has a failure branch that states what the user sees and what the system does
- every flow has at least one human step, named as a person or a role, never as a component
- `03-experience-blueprint.md` contains a table whose header row is exactly
  `| Stage | Human | AI/Agents | Systems |`
- every stage named in `02-user-flows.md` appears as a row in that table, and the counts match
- both files end with the stamp line

Run these and record what you observe:

```
rg -c '^### failure branch' docs/architecture/02-user-flows.md
rg -c '^### human step' docs/architecture/02-user-flows.md
rg -n '^\| Stage \| Human \| AI/Agents \| Systems \|' docs/architecture/03-experience-blueprint.md
```

Both counts equal the number of flows, or the gate is `FAIL`. A blueprint table missing a stage that
the flows name is `FAIL` too: the later stages cost, secure, and evaluate against that stage list.

## Step 5 — record the result

Update `docs/architecture/architecture.json`: set `gates["gate.flow"].status`, set `.evidence` to the
counts and pointers you observed, leave `verified_by` as `null`, add both files to `artifacts`, and
set `generated_at` to today.

## Stop conditions

1. A flow contains an irreversible action and has no human step. Report it; do not invent an
   approver.
2. A human step is named as a component rather than a person or a role.
3. A failure branch says only that an error is shown. What the user sees and what the system does
   are two separate answers.
4. A stage appears in the flows and not in the blueprint table, or the reverse.
5. Either output file already exists, so the agent wrote a `.proposed.md` variant beside it.
6. A human gate named in SOP.md is reached.
