# /architect — lifecycle router

This command runs nothing itself. It reads state, decides which stage is next, dispatches that
stage's agent, records the gate result, and stops. It is re-entrant: running it again after a
stop picks up where it left off. Argument: `$ARGUMENTS`.

Work in the repository the user is in. The artifact root is `docs/architecture/` relative to the
repository root. Never write outside it.

## Step 1 — load the standard operating procedure

Read `docs/architecture/SOP.md`.

If it does not exist, read `${CLAUDE_PLUGIN_ROOT}/templates/SOP.md` instead and use that as the
procedure for this run. (If your harness does not substitute `${CLAUDE_PLUGIN_ROOT}`, the same
file is at `templates/SOP.md` inside the installed plugin directory.) Do not copy the template
into `docs/architecture/` here — the `operate` stage owns that file and writes it.

SOP.md governs model routing, write scopes, stop conditions, human gates, and escalation. Where
SOP.md and this command disagree, SOP.md wins. Say in your first line which of the two files you
loaded.

## Step 2 — parse the stage table

Read `docs/architecture/WORKFLOW.md`, or `${CLAUDE_PLUGIN_ROOT}/templates/WORKFLOW.md` if the
repository has none yet.

Parse the markdown table under the heading `## Stage table`. Its columns are, in order:
`stage | agent | input | output | gate`. Take the stage order from the row order. Do not hardcode
the stage list from memory — a customer may have added a stage, and the file is the contract.

Record what you parsed as a compact list (`stage → agent → gate`) before continuing. If the table
is missing, has different columns, or has zero rows, stop and say so: this is a corrupted
workflow file, not a stage to run.

## Step 3 — find the next incomplete stage

Read `docs/architecture/architecture.json`.

If it does not exist, no stage has run. The next stage is the first row of the stage table.

If it exists, walk the stage rows in table order and take the first stage whose gate is not
complete. A gate is complete when `gates["<gate.id>"].status` is `PASS`, or `SKIPPED` with a
non-empty reason. Every other case — `FAIL`, absent from the `gates` map, missing `status` — is
incomplete.

Argument overrides, applied before this walk:

- `--stage <id>` — run exactly that stage, whatever its gate says. Use it to re-run one stage.
- `--from <id>` — start the walk at that stage instead of the first row.
- anything else — treat the argument as the goal sentence. If `architecture.json` already exists
  and its `goal` differs from the argument, stop and ask which goal is current; do not silently
  re-frame a system that is already half designed.

## Step 4 — check the gate ahead of you

Before dispatching, look at the gate of the stage *before* the one you are about to run.

If that earlier gate is `FAIL`, do not dispatch. Print the fix-first line and stop:

```
fix first: <gate.id> — <the one thing that is missing> — run /architect-<stage>
```

When `gate.decisions` is the red gate and more than one decision is `OPEN`, name the decision to
fix first in the order `trust`, `run`, `loop`, `model`, and put that decision id in the line:

```
fix first: gate.decisions/trust — <what is missing> — run /architect-decide
```

Stopping at a red gate is the point of this command. Never carry a red gate forward by starting
the next stage "in parallel" or "provisionally".

## Step 5 — dispatch the stage agent

Dispatch the agent named in the stage row using the Agent tool (`Task` in some harnesses), with
`subagent_type` set to the agent id exactly as the table spells it — for example
`discovery-analyst`. Do not do the stage's work in this context. The stage agents carry their own
write scopes and stop conditions, and those only apply inside their own context.

The dispatch prompt must contain, and nothing more:

1. the goal sentence, from `architecture.json.goal` or from the argument on a first run
2. the absolute path of the repository root and of `docs/architecture/`
3. the stage id and its gate id
4. the input files named in the stage row, as paths
5. the output files named in the stage row, as paths
6. this line verbatim: `Write only the output files listed above. Never overwrite an existing file — write <name>.proposed.md beside it and say so. End every generated markdown file with: Generated by AI Architect · https://www.frankx.ai/ai-architect`
7. the gate's green condition, copied from the gate table in WORKFLOW.md

## Step 6 — record the result

When the agent returns, read the files it claims to have written and check them against the
gate's green condition yourself. An agent's self-report is not a gate result.

Then update `docs/architecture/architecture.json`:

- set `gates["<gate.id>"].status` to `PASS` or `FAIL`
- set `gates["<gate.id>"].evidence` to the pointers you checked — file paths with line numbers,
  or commands with their observed output
- leave `verified_by` as `null`. Only the `verify` stage sets it, and only to
  `independent-verifier`
- add any new file to the `artifacts` array
- keep `schema` as `ai-architect.architecture.v1` and update `generated_at` to today

If `architecture.json` does not exist yet, create it from `${CLAUDE_PLUGIN_ROOT}/templates/architecture.json`,
filling the goal and today's date. That is the one file this command may create directly.

## Step 7 — report and stop

Print exactly four things:

1. the stage you ran and the gate result
2. the files written, as paths
3. the next stage, or the fix-first line if the gate you just recorded is `FAIL`
4. the command to run next — `/architect` to continue, or `/architect-<stage>` to redo one stage

Then stop. One stage per invocation. A run that quietly executes four stages hides which one
introduced the mistake, and the whole design of this workflow is that each gate has a place to
fail.

## When you are done with every stage

When every gate in the table is `PASS` except `gate.verify`, run `/architect-verify` — it must
run in a fresh context, which is why it is a separate command and not a step here. When
`gate.verify` is also `PASS`, print the path of the receipt and stop.
